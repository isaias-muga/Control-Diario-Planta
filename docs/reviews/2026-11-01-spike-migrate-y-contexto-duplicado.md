# Spike B0-2: `Migrate()`, pending model changes and a duplicated `AppDbContext`

- **Issue:** #26, milestone B0 (part 2 of 2). Spec: `docs/specs/B0-spike.md`, "Issue B0-2".
- **Date:** 2026-11-01.
- **Versions:** EF Core 10.0.12 (`Microsoft.EntityFrameworkCore.SqlServer` 10.0.12), `Microsoft.Data.SqlClient` 6.0.0, SQL Server LocalDB (`MSSQLLocalDB`, SQL Server 2025 17.0.4025.3), .NET SDK 10.0.401.
- **Method:** a throwaway runner under `artifacts/spike-b0-migrate/` (git-ignored, not in `DairyControl.slnx`, not committed). It references the real `DairyControl.Infrastructure` project (so the real `AppDbContext`, its 10 migrations and its snapshot are used) and changes nothing under `src/`. Instead of editing a copy of the code, the "changed model" of M2, M3, M4 and M8 is made with a custom `IModelCustomizer` that runs after the real configuration (M2 to M4: one extra shadow property `ExtraSpike` on `Proveedor`; M8: `ToTable(<same name>, "dbo")` on `Proveedor`), plus a custom `IModelCacheKeyFactory` so each variant gets its own model. Each LocalDB database was created by the spike and dropped at the end (4 databases, all dropped).

## Results

| # | Case | Observed result |
|---|---|---|
| M1 | Real `AppDbContext`, current snapshot, `Database.Migrate()` on an empty database | Succeeded. `__EFMigrationsHistory` has 10 rows, 10 migrations in the assembly. |
| M2 | One property added to an entity (pending model change), `Migrate()` | **Throws** `System.InvalidOperationException: An error was generated for warning 'Microsoft.EntityFrameworkCore.Migrations.PendingModelChangesWarning': The model for context 'AppDbContext' has pending changes. Add a new migration before updating the database. See https://aka.ms/efcore-docs-pending-changes. This exception can be suppressed or logged by passing event ID 'RelationalEventId.PendingModelChangesWarning' to the 'ConfigureWarnings' method in 'DbContext.OnConfiguring' or 'AddDbContext'.` |
| M3 | M2 plus `ConfigureWarnings(w => w.Ignore(RelationalEventId.PendingModelChangesWarning))` | `Migrate()` succeeded and the history table was written (10 rows). |
| M4 | `HasPendingModelChanges()` with a connection string to a server that does not exist (`(localdb)\NoExisteSpike`, `Connect Timeout=3`) | It **does not appear to open a connection** (inferred from the fast answer and the absence of any exception against a missing server): answered in 58 ms (unchanged model) and 53 ms (changed model). Returned `False` for the unchanged model and `True` for the changed one. |
| M5 | A context with an empty model (no entities) pointed at the migrations assembly of `AppDbContext`, `Migrate()` | Succeeded and did nothing: 0 migrations found for it, 0 rows in the history table (the table is created). The snapshot was **never applied** to the empty model, so this run does not answer whether an empty model against the `AppDbContext` snapshot behaves like M2: no `PendingModelChangesWarning` appeared because there was nothing to compare. The reason is an inference, not observed: the migrations and the snapshot carry `[DbContext(typeof(AppDbContext))]`, so a different context type finds none of them. A run with the attribute retargeted was not done. |
| M6 | Two projects both defining `DairyControl.Infrastructure.Persistence.AppDbContext`, a third referencing both and using the type with no `using` through a project-level `<Using>` | Does **not compile**: `error CS0433: The type 'AppDbContext' exists in both 'Dup1, Version=1.0.0.0, ...' and 'Dup2, Version=1.0.0.0, ...'`. It is an error by default, so `TreatWarningsAsErrors` makes no difference (same result when the property was set to `false` and then to `true` in the throwaway project files; they were left at `true`). |
| M6 (supplementary) | A project that defines the type itself and also references one project that defines it | Compiles with `warning CS0436: The type 'AppDbContext' in '...AppDbContext.cs' conflicts with the imported type 'AppDbContext' in 'Dup1 ...'. Using the type defined in ...`. With `TreatWarningsAsErrors=true` (as `Directory.Build.props` sets) CS0436 is an error. |
| M7 | The project that uses the type references only one of the two | Compiles with no warning and no error (0 and 0), with `TreatWarningsAsErrors` `false` and `true`. |
| M8 | `ToTable(name, "dbo")` on `Proveedor` against the real snapshot (which has no explicit schema) | `HasPendingModelChanges()` = **`True`**: an explicit `dbo` is a pending change, not equal to no schema. Fallback for B1b-3: a legacy `AppDbContext` must not call `ToTable(..., "dbo")`, and a test of a module context should assert that its schema is unset where the snapshot has none (record only; no migration is allowed and a null schema in `MapHistory` would change the Kernel.Persistence contract): the decision goes to the tech lead; the model of the legacy `AppDbContext` must keep leaving the schema unset. |

## Decisión

1. **Is `PendingModelChangesWarning` an error in `Migrate()` on this EF Core version?** Yes, EF Core 10.0.12 throws `System.InvalidOperationException` (M2).
2. **The line that silences it for a frozen context:** `.ConfigureWarnings(w => w.Ignore(RelationalEventId.PendingModelChangesWarning))` on the context options (`using Microsoft.EntityFrameworkCore.Diagnostics;`), which made `Migrate()` succeed (M3).
3. **Does `HasPendingModelChanges()` need a database connection?** No: against a server that does not exist it answered in about 55 ms with no exception (`False` unchanged, `True` changed), so the guard test "Prueba guarda HasPendingModelChanges del AppDbContext" of B1 can run without SQL Server, building the context with `UseSqlServer(...)` on a server that does not exist and never connecting (the spike used `Server=(localdb)\NoExisteSpike;...;Connect Timeout=3`; the connection string named in the B1 issue was not run).
4. **Does a duplicated `AppDbContext` compile?** No when one project references both (M6): `CS0433`, an error in any configuration; yes when the project that uses it references only one of the two (M7, no diagnostics); a project that defines the type itself and references another that defines it compiles only with `CS0436` as a warning, which the repo's `TreatWarningsAsErrors` turns into an error, so the frozen `Legado` project must be the only one that defines `AppDbContext`, as ADR 0005 says.
